# Windows releases and updates

NEXUS only checks for updates when a user asks. It looks at up to the 100 most recent public GitHub releases of `mafk21/NEXUS`, not GitHub Actions artifacts, source commits, or unpublished builds. Windows packages compare their own `package.json` version with valid `v`-prefixed release tags. A prerelease installation can see newer stable and prerelease versions; a stable installation sees stable releases only. An available update must have an uploaded asset named exactly `NEXUS Setup <version>.exe`, with a GitHub SHA-256 digest and a size no larger than 512 MiB. Older builds without the button cannot update themselves: install a version that includes it manually first.

## For users

In the packaged Windows app, open **Settings → Check for updates**. If a newer release has a verifiable Windows installer, choose **Download update**. NEXUS downloads it and checks its size and SHA-256 digest against GitHub. Then choose **Install update** and confirm to open the installer and close NEXUS. You may cancel before confirmation; you can also view the release page instead. The installer can still require your input. The checksum only checks against GitHub's metadata; it does not authenticate the publisher. Current installers are unsigned; consider Windows' warning before deciding to run them. The real download, update, and user-data retention have not yet been verified end to end; back up important data first. Source-built copies with identical version numbers may contain different code and cannot be distinguished by this checker. Linux/Chromebook and browser update checks are not supported.

If no compatible release is published, the checker reports that none are available. A temporary Actions artifact is not a release. No account is required to check the public releases endpoint; GitHub can log the request. See [privacy](privacy.md) and [security](security.md).

## For maintainers

Releases are **not published automatically** by ordinary builds, PRs or tag pushes. Only a repository maintainer who intends to distribute a release should publish one. Never repoint an existing release tag or replace a released installer.

1. Review the code, dependencies, release notes, licensing, and Windows behavior. Increment the SemVer version in both `package.json` and `package-lock.json` (for example with `npm version <new-version> --no-git-tag-version`). It must be strictly newer than the previous published release; every distinct release needs a new version. Verify the versioned code and normally merge it to main before tagging; if a release is explicitly authorized from a reviewed release branch, record its exact commit and merge the version change afterward.
2. Create and push an annotated tag `v<version>` pointing at the reviewed commit, following the repository's authorization and release practices. The tag must already exist; do not force-push it. Tag names with build metadata are not supported by the publishing workflow.
3. Manually run **Publish Windows release** in GitHub Actions and enter the existing tag. The workflow checks the version and lockfile, audits, tests, builds, and smoke-tests Windows before creating the GitHub release with its Windows installer. Versions with a prerelease suffix are marked prerelease. It needs the Actions `GITHUB_TOKEN` with contents-write permission and repository settings that permit release creation. If any check fails, it does not publish.
4. Check the published page, expected installer name and release notes. The workflow does not sign the installer. Test a real update from an older installation separately before relying on it; normal CI smoke tests do not install or upgrade NEXUS.

The update service constructs the GitHub release download URL from a validated version and restricts redirect hosts, checks the asset size and SHA-256 digest, and asks before launching it. A GitHub checksum is not an independent signature. Secure repository access and establish code signing before presenting updates as authenticated. GitHub must expose its `digest` metadata for the installer; otherwise the app reports no verifiable installer. The Windows CI workflow remains build-only and never publishes a release.
